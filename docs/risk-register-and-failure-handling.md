# リスク台帳・異常系処理・受け入れ仕様

- 文書種別：横断的な品質・障害対応仕様
- ステータス：**PROPOSED（実装済みを意味しない）**
- 対象：PG62 GC先物、PG64 OG金オプション、COT、FRED、履歴、分析、画面、ローカル運用
- 最終更新：2026-10-21

本書は想定可能な失敗モードを一覧化し、必須の処理・表示・テスト条件を定める。コード、テスト、実データ検証の証拠が揃うまで「仕様化済み／実装未確認」と扱う。文書があるだけで実装済み、正確、運用可能とはみなさない。

## 1. 基本原則

1. **Fail closed**：解釈・来歴・版・日付・契約キーが未確定なら確定履歴や分析入力へ昇格させない。
2. **欠損を推測で埋めない**：未取得、未掲載、ゼロ、明示的な空欄、非数値記号、解析失敗を別状態として保持する。
3. **不一致を伝播させる**：上流レコードが未確認または不正なら、依存する派生値も未確認とし、下流だけの算術一致で正当化しない。
4. **追記型・再現可能**：原本と処理結果を上書きせず、入力ハッシュ、処理版、規則版、実行時刻を結びつける。
5. **証拠を区別する**：同じPDFの別テキスト抽出、同じ座標規則の再実行、AIによる再読だけを独立証拠とみなさない。
6. **データ品質と公開可否を混同しない**：個人用ローカル運用を前提とする。公開経路は現行スコープ外であり、非公開データを公開Pagesへ含めない技術的分離を維持する。
7. **状態は明示する**：RAW_REGISTERED、EXTRACTED、NOT_CHECKED、INCOMPLETE、QUARANTINED、VALIDATED、SUPERSEDED、FAILEDを区別する。既存状態との統合時は意味を変えず、マッピング表を用意する。

## 2. 横断的なデータ契約

正規化レコードは利用可能な範囲で以下を保持する。

- 識別：source/document ID、bulletin type/number/date、edition/status、page、section、row/token reference
- 時間：trading_date、bulletin_date、open_interest_as_of、retrieved_at、known_at、タイムゾーン／日付規則版
- 商品：product/root、contract identifier、expiry、option type、strike、単位
- 値：原文文字列、正規化値、値の状態、符号、正規化ルール版
- 来歴：PDF SHA-256、抽出器名・版、schema/rule/master version、実行ID、親レコードID
- 検証：検査ID、結果、比較対象レコード、未確認理由、証拠参照、検査時刻

原文と正規化値を上書きで混在させない。値が存在しない場合に0を代入しない。既存スキーマで全項目を持てない場合は、欠けている項目を明示し、黙って値を捏造しない。

## 3. 日付・前日比較・連鎖誤り

### 3.1 比較対象の選択

- カレンダー上の前日ではなく、確認済み取引日カレンダー、対象商品、同一契約識別子、版状態を使って比較対象を選ぶ。
- 比較対象は「前にファイルに存在した行」だけで決めない。入力期間内に欠落bulletinがないか、対象日が期待される公表日かを確認する。
- 休日は、検証済みカレンダーと公表実績で説明できる場合のみVERIFIED_HOLIDAY_GAPとする。単に日付が飛んでいるだけで休日と推定しない。
- 欠落日が疑われる場合はMISSING_BULLETIN、初回観測はFIRST_OBSERVATIONとし、算術ゲートをPASSにしない。
- 比較元は同一商品の同一契約・同じ意味の項目でなければならない。限月ロール前後を同一契約として比較しない。

### 3.2 例外理由コード

| コード | 意味 | 必須処理 |
|---|---|---|
| FIRST_OBSERVATION | 比較できる過去観測なし | NOT_CHECKED。PASSにしない |
| VERIFIED_HOLIDAY_GAP | カレンダーと公表記録で説明できる休場 | 前回有効観測との比較可否を項目定義に従って判定 |
| MISSING_BULLETIN | 期待される日付の資料がない | INCOMPLETE。連続日チェックを停止 |
| NEW_CONTRACT | 新規限月で過去値がない | NOT_CHECKED。別契約の値を代用しない |
| EXPIRED_CONTRACT | 満期等で当日行がない | 終了理由を記録。ゼロ値や差分を作らない |
| ROLL_TRANSITION | 中心限月が切り替わった | 限月別系列を維持。未確定の連続系列差分を作らない |
| PRELIMINARY_EXCLUDED | PRELIMINARY観測 | FINAL算術比較に使わない |
| UNRESOLVED_VALUE | 値または符号の意味が未確定 | NOT_CHECKEDまたはQUARANTINED |
| SOURCE_DATE_AMBIGUOUS | bulletin/trading/OI基準日を確定できない | 自動補正せず隔離 |
| UPSTREAM_INVALID | 比較元が不一致・隔離・未確定 | 依存する後続検査もNOT_CHECKED |

理由コードは根拠なく付与してはならず、必要に応じ複数を記録する。

### 3.3 GC算術検査

候補式は以下。ただし運用ゲートとして有効化する前に実PDFの項目定義を確認する。

- Settlement差分：settlement(t) − settlement(reference) == reported_price_change(t)
- OI差分：open_interest(t) − open_interest(reference) == reported_oi_change(t)

referenceは仕様上検証済みの比較対象を指す。OI Changeの基準日が前回公表日と一致することを実PDFで確認するまでは、OI差分検査はOPEN/NOT_CHECKEDとし、成功扱いしない。十進演算で厳密比較し、不一致を許容誤差で吸収しない。

- 同一日・同一版・同一契約の重複キーはブロックする。
- FINAL同士だけを確定算術に用いる。PRELIMINARYをFINALの比較元にしない。
- 確認済み算術不一致が1件でもあれば対象をBLOCKED/QUARANTINEDとする。
- 欠損・未解決・比較対象不明があれば全体結果はPASSではなくINCOMPLETE。
- 適用可能な全検査が実行され、一致し、未解決の重大事項がない場合のみPASS。

### 3.4 連鎖誤り・再検証

- レコードの検証状態を、依存する比較・集計・グラフ系列へ伝播する。
- 前日値が訂正された場合、その値を比較元に使った全後続日・派生値を特定して再検証する。
- 依存元がQUARANTINED、INCOMPLETE、SUPERSEDEDの場合、後続の算術一致だけでVALIDATEDに昇格させない。
- 再計算前の結果は削除せず、旧結果をSUPERSEDEDとし、新しい実行ID・入力ハッシュと結びつける。
- 同じ誤値が複数日に繰り返されると差分検査を通過し得る。算術検査は原本画像確認や独立照合の代替ではない。

## 4. PDF・抽出・意味解釈のリスク

| リスク | 必須対策 | 受け入れテスト |
|---|---|---|
| PDFの取り違え・破損・暗号化 | SHA-256、ページ数、bulletin ID/date/editionを記録。不一致は停止 | 同一名別ハッシュ、暗号化・破損PDF、ページ数不一致を拒否 |
| ページ欠落・重複・順序違い | 期待ページ数、印字Side番号、重複指紋を検査 | 欠落・重複・順序入替を検知 |
| PRELIMINARY/FINAL/訂正版の混同 | editionを明示管理し、訂正版は追記 | 同日複数版が通常履歴で混ざらない |
| 読み順・列・行の誤結合 | raw token、位置、見出し、列定義、行識別を保持 | 列ずれ、複数行結合、改行分割、順序変更を検知 |
| 符号・特殊トークンの誤変換 | 原文保持。----、UNCH、B/A、独立符号を意味定義なしに数値化しない | 正負、分離符号、特殊記号、未知グリフをテスト |
| 誤った契約・項目への割当て | 一意なfield/contract keyと定義版。曖昧なら隔離 | 同名限月、見出し変更、未知契約をテスト |
| 解析器の差・バージョン差 | parser/versionを記録し差分を調査 | 解析器更新時に変更行・トークンを比較 |
| 見た目の異常をテキスト検査が見逃す | 重要項目を原本ページ画像で確認 | GC主要項目の画像照合記録 |
| 合計だけ一致する誤抽出 | TOTALを補助検査とし、行単位で照合 | 行の値を入れ替えて合計を保つ異常を検知 |
| レイアウト変更 | fingerprint不一致を検知し未承認レイアウトを隔離 | 見出し・座標・ページ数変更で承認解除 |

### 4.1 独立証拠の条件

同じPDFのテキスト層を別ライブラリで読み直すことは差分検出に有用だが、それだけで独立した正解証拠にはならない。主要値の承認では、原本画像の人手確認、項目定義が確定した算術整合、必要な独立参照、parserとは別の方法で作成したgolden fixture／レビュー記録を組み合わせる。

## 5. 商品・限月・ロール

- 連続系列は限月別原データを上書きして作らない。
- 中心限月の選定は出来高最大・OI最大など候補ルールを区別し、確定したロール規則と規則版を記録する。
- ロール日の価格差を通常の価格変化として扱わない。調整済み連続系列を作る場合は調整方式と未調整値を両方保持する。
- 新規限月、最終取引日、満期等で行が消える場合、ゼロOIやゼロ出来高に置換しない。
- GC先物、OGオプション、COMEX、GLD等を日付や似た名称だけで結合しない。検証済みマッピングがなければ隔離する。
- テストは限月追加・消滅、出来高/OI順位逆転、ロール日、重複契約名、異なる商品コードを含める。

## 6. 履歴・再実行・訂正・時点整合性

- 原本、抽出マスター、正規化レコード、検証レポート、派生指標を別層として保持する。
- 同一入力・同一コード・同一設定の再実行は冪等とし、重複レコードを作らない。実行ログは別途記録する。
- 訂正は新しい版として追記し、旧版との差分を記録する。最新ビューを作っても過去版を復元可能にする。
- 後日取得した過去データのknown_atを過去の公表日時に偽装しない。歴史的公表時刻が不明なら不明とする。
- バックテストは当時利用可能だった値だけを参照し、後日訂正・将来データを混ぜない。
- マスター・スキーマ・ルール変更時は影響範囲、再計算計画、旧版との比較を記録する。

## 7. COT・FRED・外部系列

- API取得成功と最新性・正確性を別々に判定する。
- HTTPエラー、レート制限、タイムアウト、空レスポンス、スキーマ変更、部分データを検知し、最後の成功値を新しい値として偽装しない。
- 欠損値をゼロ・補間・前方補完で埋めない。研究用補完を行う場合は別系列として方式を表示する。
- 取得日、公表日、対象期間、改訂履歴、単位を保持する。
- 鮮度閾値は頻度ごとに設定する。週次COTと日次金利に同じstale閾値を使わない。
- テストに欠損、重複、古いデータ、改訂値、スキーマ変更を含める。

## 8. 分析・計算

- 観測値、決定的計算値、仮定付き推定値、シナリオをデータモデルとUIの双方で区別する。
- GEX等はOI基準日、IV/Gamma単位、契約倍率、符号仮定、満期窓、原資産の時間整合を検証する。
- OIはディーラーのネットポジションそのものではない。観測できないディーラー符号を断定しない。
- 単位変換、丸め、通貨、契約倍率を計算式・版に含める。丸めは表示層で行い、内部計算を途中で丸めない。
- 予測・売買シナリオは、ベースライン、時系列順検証、point-in-timeデータ、手数料・スリッページを含む評価なしに有効性を主張しない。
- 計算結果には入力参照・式・規則版を結びつけ、再現可能にする。

## 9. UI・配信・状態表示

- 各パネルに対象日、取得／更新時刻、版状態、検証状態、鮮度、ソースを表示する。
- 欠損・未確認・隔離・古いデータを空白やゼロで隠さない。確認中、未取得、古い、要調査などを明示する。
- 取得失敗時に前回値を表示するなら「前回成功時の値」と日付を表示する。
- 中心限月の切替時は対象限月と選定根拠を表示する。ロール差を通常の価格変化に見せない。
- ローカル専用データと公開成果物を別ディレクトリ・別生成経路・別CI対象に分ける。公開ビルドへ非公開入力を与えず、成果物に混入がないことを自動テストする。
- UIを正常・欠損・古い・隔離・取得失敗の各状態で確認する。

## 10. 運用・環境

- 手動PDF取込は入力パス、ハッシュ、識別情報、実行ID、結果レポートを残す。ファイル名だけを信用しない。
- 自動処理はタイムアウト、再試行回数、バックオフ、重複防止、失敗通知を定義する。無限リトライは禁止。
- APIキー等をソース・ログ・公開成果物へ出さず、設定値と秘密情報を分離する。
- 依存パッケージと実行環境を固定し、更新時に回帰テストを実行する。
- バックアップ、復元、履歴破損時のロールバック手順を整備し、復旧後に件数・ハッシュ・主要値を確認する。
- 非公開データが公開対象へ追加されたらビルドを失敗させる。

## 11. テストマトリクスと受け入れゲート

最低限、以下をfixtureまたは実データでテストする。

1. 通常の連続FINAL日・複数契約
2. 週末・検証済み休日を挟む日付
3. 期待されるbulletinの欠落
4. 新規限月、満期・行消滅、ロール日
5. PRELIMINARYのみ、FINALへの置換、同日訂正版
6. 同一契約の重複行、同一日の重複bulletin
7. Settlement差分不一致、OI差分不一致
8. 前日値が不正・隔離された後続日（連鎖誤り）
9. OI基準日不明、bulletin dateとtrading dateの不一致
10. ----、UNCH、B、独立符号、空欄、未知文字
11. ページ欠落・重複・順序変更・レイアウト変更
12. 同一PDFの再実行、訂正版再実行、parser版変更
13. APIタイムアウト、部分レスポンス、古い値、改訂値
14. ローカル専用データが公開成果物へ混入するケース
15. UIの正常・未確認・隔離・古い・取得失敗の各状態

- **Gate A — Source identity**：原本識別・ハッシュ・版・ページ構成が確認済み。
- **Gate B — Extraction structure**：対象ページ・行・必須列が検出され、全トークンの処遇が定義済み。
- **Gate C — Semantic correctness**：フィールド定義・単位・符号・特殊トークン・OI基準日が根拠付きで確定。
- **Gate D — Arithmetic and continuity**：比較対象日・契約が正しく、適用可能な算術が一致し、欠落・連鎖誤りが未解決のまま通過していない。
- **Gate E — Independent evidence**：主要項目の原本画像照合と必要な独立参照が記録済み。
- **Gate F — History integrity**：冪等性、訂正追記、point-in-time再現、再計算範囲がテスト済み。
- **Gate G — UI and operations**：状態表示、鮮度、エラー、再処理、復旧が確認済み。
- **Gate H — Local/public separation**：非公開データが公開生成物へ含まれないことを自動検査できる。

適用ゲートが未達ならDIAGNOSTIC_ONLY、INCOMPLETE、QUARANTINED等を維持し、確定データとして表示・利用しない。合格は対象・期間・バージョンに限定して記録する。

## 12. 未決事項と決定ルール

次は実PDF・公式仕様・実装証拠を得るまでOPENとする。

1. PG62のOI Changeがどの日付のOIを基準にするか、休日・訂正版で例外があるか。
2. 取引日カレンダーと各bulletin typeの期待公表日。
3. GCの契約キー・満期・ロール規則、および連続系列の調整方式。
4. ----、UNCH、B等の項目別意味と適用範囲。
5. 主要フィールドの実PDF照合範囲、連続する実データの日数、受け入れ閾値。
6. 既存cme-gc-history.jsonの互換性・移行・ロールバック計画。
7. 公開Pagesとローカル専用データの分離が現在のCI／生成フローで保証されているか。

未決事項はタスク・必要な証拠・影響ゲート・次の確認方法をSTATUS記録へ登録する。根拠なく「通常はこう」と決めて仕様を確定しない。

## 13. 実装順序

1. 既存算術ゲートへ例外理由コードと連鎖誤りの伝播を追加する。
2. 実PDF複数日でOI Changeの基準日を確認し、根拠と判定を記録する。
3. 取引日・bulletin期待日・契約ライフサイクルのマスター／検査を追加する。
4. GCの抽出→検証→履歴→UIを一連の処理として接続する。
5. 異常系fixtureと実PDF回帰ケースを追加し、未達ゲートをレポートする。
6. COT/FREDの鮮度・欠損・改訂状態を共通契約へ接続する。
7. GCが安定してからPG64の対象項目を同じ品質ゲートへ接続する。
8. 分析指標・自動化は上流データのゲートが合格してから進める。

各要件は実装ファイル・テストケース・実データ検証レポートを進捗記録へ結びつけ、未確認を完了と誤認しないこと。
