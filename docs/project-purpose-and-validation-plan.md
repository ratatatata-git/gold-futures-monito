# Gold Futures Monitor：目的・実現方式・実装／テスト計画

- 文書ステータス：作業方針の合意用ドラフト
- 対象リポジトリ：`ratatatata-git/gold-futures-monito`
- 公開Webアプリ：https://ratatatata-git.github.io/gold-futures-monito/\n- [データ状態遷移と日付定義（設計案）](data-state-and-date-contract.md)
- 主対象市場：COMEX Gold（GC）先物および関連オプション
- 最終更新：2026-10-14

## 1. 目的（Why）

本システムの目的は、ゴールド市場についてファンダメンタルズ分析と需給・ポジショニング／フロー分析を組み合わせ、デイトレードおよびスイングトレードの判断材料を提供することである。

- **ファンダメンタルズ**：金価格が中長期的にどちらへドリフトしやすいかを考える。
- **フロー／ポジショニング**：どの参加者が、どのような条件で、どちら向きの売買を行う可能性があるかを推定し、タイミングを考える。
- **統合**：長期的な方向性、ポジションの偏り、オプション構造、価格モメンタムが同じ方向を示しているかを整理する。

本システムは売買を自動執行するものではなく、観測データと推定を区別した意思決定支援ツールとする。

## 2. 現在の作業範囲（What：いま検証していること）

**現在の最優先事項は、COMEX Daily Bulletin の PG62・PG64 PDFから必要な情報を正確に抽出できることの検証である。** 分析指標の追加やトレードシグナル開発は、この検証を置き換えるものではない。

### PG62／PG64検証の目的

1. PDF上に記載された値・記号・符号を欠落や改変なく読み取る。
2. 抽出した値を正しい日付、商品、限月、項目、列に割り当てる。
3. ページ内の見出し・表構造・行の識別情報を軸に、別の値が混ざったり順序が変わったりしないことを確認する。座標はセルの列所属などを判定する補助証拠とし、固定のページ位置を行・限月の識別ルールにしない。
4. 検証済みデータだけを、後段の履歴データおよびWebアプリへ渡せるようにする。

### 現在の作業と、その限界

- PR #20：座標ベースの行グルーピングに関する合成データテスト。
- PR #21：行グルーピング時のraw token保持に関する合成データテスト。
- 上記はテスト範囲を補強するが、実際のCME PDF全体における抽出精度を証明するものではない。
- 実PDFとの照合、列・限月への割当て、履歴データへの安全な反映は別途検証する。
- 本番利用の判定状態 `BLOCKED_DIAGNOSTIC_ONLY` は、明示した合格条件を満たすまで維持する。

## 3. 最終的に実現するもの

公開Webアプリ [Gold Futures Monitor](https://ratatatata-git.github.io/gold-futures-monito/) に、検証済みデータを用いたゴールド先物・オプションの分析結果を反映する。

想定する段階的な機能：

1. GC先物の限月別データ（価格、出来高、OI等）の閲覧と履歴推移。
2. 価格変化とOI変化の組合せによるポジショニング状況の整理。
3. CFTC COTレポートによる参加者区分別ポジションの週次分析。
4. COMEX金オプションのストライク別OI・出来高・IV・満期情報の可視化。
5. オプション建玉の集中価格帯、想定されるサポート／レジスタンス、ガンマ関連の推定指標。
6. CTA等のトレンド追随フローが発生し得る価格帯の推定。
7. ファンダメンタルズとモメンタムを加えたシナリオ表示。

上記は最終構想であり、すべてが現時点で実装済みであることを意味しない。実装は抽出品質とデータ可用性を確認しながら段階的に進める。

## 4. 実現方法（How）

### 4.1 データの流れ

```text
CME Daily Bulletin PDF（PG62 / PG64）
        ↓
原本保存（SHA-256・版種・取得時刻）
        ↓
全ページの抽出マスター（raw token・構造・証跡）
        ↓
実PDF照合・品質検証（失敗時は隔離）
        ↓
バージョン付き規則による派生データ
   ┌────┴──────────┐
PG62先物正規化データ     PG64オプション正規化データ
   ↓                         ↓
限月判定・連続系列      オプション分析指標
   └──────────┬──────────┘
              ↓
公開審査済みの配信用データ
              ↓
公開Webアプリ
```

`data/cme-gc-history.json` は、PDF抽出から直接書き込む先として扱わない。既存履歴の移行先・互換性・ロールバック方式を定義したうえで、必要な派生データを提供するビュー／成果物として位置づける。原本版種・処理状態・公開状態と日付フィールドの規約は [データ状態遷移と日付定義](data-state-and-date-contract.md) を参照する。

### 4.1.1 PDF抽出ロジックの基本方針

座標を全面的に捨てるのでも、座標だけで解釈するのでもない。次の順序で構造を復元する。

1. **入力ソースを確定する**：ファイル名だけに依存せず、PDFのSHA-256、印字されたbulletin date／number／FINAL・PRELIMINARY、ページ数を記録する。
2. **ページごとの証拠を抽出する**：テキストトークン、必要な文字単位の位置情報、ページ番号を保持する。読み取り順だけで表の意味を決めない。
3. **見出しとセクション境界を検出する**：商品ヘッダー、CALL／PUT、満期、列見出し、TOTAL等の明示されたテキストを使って表の領域と意味を決める。商品・満期などが確定しない領域は未解決にする。
4. **表ごとに列構造を復元する**：列見出しの文字と、その表の中で観測した横方向の配置を照合する。絶対座標を全ページ共通の列定義として固定しない。列位置や見出しが曖昧なら、自動で推測せず隔離する。
5. **行候補を復元する**：ストライク等の行識別候補、同じ行に属するトークンの縦位置、表の罫線・行間・局所的な配置を組み合わせる。行間やY座標のしきい値は表ごとに検証し、ページ番号や「上から何行目か」を行IDにしない。
6. **行の意味をPDFの明示情報と照合する**：商品、CALL／PUT、満期、ストライク、列見出しが一貫して解釈できることを確認する。ストライクの並び順、近隣セル、商品マスター、TOTALの計算結果だけから欠落情報を補完しない。
7. **raw tokenを先に照合する**：正規化前の抽出文字列を、独立してPDFから転記・確認したfixtureと比較する。その後で項目別に正規化し、raw token・normalized value・parse statusを別々に保存する。
8. **整合性を検査する**：重複行、欠落行、未知のヘッダー、未解決の列、異常なTOTAL範囲などを報告する。TOTALは、その項目が加算可能で、対象行の範囲がPDF上で明確な場合にだけ照合する。
9. **ページ全体・文書全体で監査する**：ページ数、セクション数、行数、解決済み／隔離行、重複、欠落、TOTAL不一致を集計する。集計値が合っていることだけで個々の行の正しさを保証しない。
10. **実PDFを使った回帰テストを行う**：行数や限月構成の異なる複数の実PDFで、抽出結果を独立確認済みfixtureと比較する。新しいレイアウトに未対応の場合は、成功したように見せず明示的に失敗・隔離する。

**重要な区別：** 座標は「このトークンが表のどの列・どの行候補に属しそうか」を判断する証拠であり、「この位置にあるから必ず特定の限月／項目である」と決める根拠ではない。ページの絶対位置、固定行数、特定限月の並び順に依存する実装は避ける。

### 4.2 データの分類

データや指標は、少なくとも次の種類に区別する。

- **Raw／原資料由来**：PDFから抽出した文字列・値・必要な場合の座標・出典。座標は診断・列所属判定の証拠であり、単独で商品・限月・行の意味を決めるものではない。
- **正規化データ**：日付、商品、限月、項目などを定義済み形式に整理した値。
- **計算値**：価格変化、OI変化、IV変化など、入力データと式から再計算できる値。
- **推定値**：CTAトリガー、ディーラーガンマの方向、想定フローなど、仮定を含む値。
- **分析結果**：複数のデータを組み合わせたシナリオや判断材料。

原資料の値を、推定や表示上の都合で黙って書き換えない。推定値には計算方法・前提・更新時点を付記する。

### 4.3 更新頻度の原則

- CME先物・オプションOI：原則として日次公表データを利用する。日中のリアルタイムOIと混同しない。
- COT：週次データとして扱い、ポジションの基準日と公表日を区別する。
- 価格・出来高・IV：提供元、契約条件、更新頻度、遅延の有無を確認してから表示する。
- OIを固定し価格を更新して算出するガンマ指標は「前回OIを用いた推定値」であり、リアルタイムのディーラー保有ポジションを示すものではない。


### 4.4 マスターデータと派生データの分離

PG64はページ数・表・行数が多いため、分析に必要な列だけを直接抽出するのではなく、まずPDF全体の抽出証拠を日付単位のマスターデータとして保存し、用途別の派生データをそこから生成する。

- **原本層**：公式PDF、SHA-256、bulletin date／number、FINAL・PRELIMINARY、ページ数など。
- **マスター層**：文書→ページ→セクション→表→行→セル／トークンの構造。raw token、座標、解決状態、診断情報を保持する。
- **分析用データ層**：マスターから正規化したオプションデータ、またはPG62等から正規化した限月別先物データを生成する。
- **中心限月判定層**：先物の限月別データから、日付別の判定結果・根拠・ルールバージョンを生成する。
- **連続チャート層**：中心限月判定から、実価格・ロールイベント・必要に応じた調整済み価格を生成する。

PG64はオプションデータのソース、PG62等は先物の限月別データのソースとして区別する。中心限月判定や連続チャートをPG64マスターに埋め込まない。各派生データには入力データのハッシュ、生成コード／ルールのバージョンを記録し、ロジック変更時に再生成・差分比較できるようにする。

マスターは監査・再処理用であり、公開Webアプリは必要な派生データを読むことを基本とする。未解決の行・列・値を捨てたり推測で埋めたりせず、診断状態を保持する。詳細なJSON構造、ファイル構成、派生データの責務、再生成ルール、初期受け入れ条件は [PG64マスター／派生データ設計案](pg64-master-derived-data-architecture.md) に定義する。状態遷移、速報／確定版、日付フィールド、point-in-time履歴の規約は [データ状態遷移と日付定義](data-state-and-date-contract.md) を参照する。既存の `data/cme-gc-history.json` は直結する抽出先ではなく、移行計画と互換性を定義したうえで派生データ層に位置づける。

## 5. 設計原則

1. **正確性を優先する**：値、符号、文字列、日付、限月、項目を推測で補正しない。
2. **原資料まで追跡できる**：抽出値とPDF上の該当箇所を照合できるようにする。
3. **不確実なデータは fail closed**：検証できないデータを本番履歴へ自動反映しない。
4. **診断と本番を分離する**：診断出力は本番データ更新と明確に区別する。
5. **テスト段階を混同しない**：合成データテスト、実PDFテスト、履歴更新テスト、公開アプリ確認は別々に判定する。
6. **変更範囲を小さくする**：失敗箇所を特定してから最小限の修正を行う。
7. **再現性を保つ**：同じ入力PDFと同じコードから、同じ抽出結果を再現できるようにする。
8. **事実と推定を区別する**：OIの偏りだけで参加者の売買方向やディーラーのネットガンマを断定しない。

## 7. テスト項目と合格条件

### 7.1 合成データによる単体テスト

- [ ] `0` が欠損・空欄に変換されない。
- [ ] `----`、`UNCH` などの表記が保持される。
- [ ] 正負の符号と符号付き変化量が保持される。
- [ ] High／Low等のB/A表記が欠落・移動しない。
- [ ] 表の範囲内での行・列復元が期待どおりであり、固定ページ位置に依存しない。
- [ ] 行の順番が変わっても異なる行の値が混ざらない。
- [ ] 欠落列、重複値、不正形式を検出できる。

**合格条件：** 期待値と実際の出力が一致し、値の改変・欠落・列ずれがない。

### 7.2 実PDFとの照合テスト

- [ ] 対象PDF、対象日付、対象ページが正しく識別される。
- [ ] PDF上の値を人が照合できる比較表または診断出力がある。
- [ ] 代表例だけでなく、対象ページの必要な行・限月・項目を網羅して照合する。
- [ ] ページレイアウトや桁数が異なるケースを確認する。
- [ ] 例外・読み取り不能・曖昧な値が黙って正常扱いされない。
- [ ] PG62とPG64を個別に検証し、ページ固有の構造差を確認する。

**合格条件：** 合意した対象範囲についてPDFと抽出結果が一致し、未解決の不一致が記録・説明されている。サンプル行だけの一致をページ全体の合格とみなさない。

### 7.3 履歴更新テスト

- [ ] 検証不合格の入力では本番履歴が変更されない。
- [ ] 合格した入力だけが期待する日付・限月に反映される。
- [ ] 既存履歴が意図せず削除・上書きされない。
- [ ] 同一PDFの再処理で重複レコードが作られない。
- [ ] 更新前後の差分が説明可能である。
- [ ] エラー時の終了状態とログが明確である。

**合格条件：** 入力に対する差分が期待どおりで、失敗時に本番データが保護される。

### 7.4 CI／公開アプリのテスト

- [ ] 関連する自動テストとCIが成功している。
- [ ] 生成された履歴ファイルがスキーマ検証を通過する。
- [ ] Webアプリが正常にデータを読み込む。
- [ ] 表示値を履歴データの元レコードまで追跡できる。
- [ ] 公開URLで、日付・限月・数値・空欄表示が正しい。

**合格条件：** CI成功だけで完了とせず、成果物と公開画面の確認まで完了する。

## 8. 本番反映ゲート

状態 `BLOCKED_DIAGNOSTIC_ONLY` は、少なくとも次の条件を満たすまで維持する。

1. 合成データのテストが通過している。
2. PG62／PG64の実PDFで対象範囲の照合が完了している。
3. 未解決の抽出不一致がない、または明示的に隔離されて本番反映対象外になっている。
4. 履歴更新の安全性テストが通過している。
5. CIと成果物の検証が完了している。
6. 本番反映を許可する条件と、その根拠が記録されている。

具体的な許容差や対象PDFの本数など、リポジトリでまだ明文化されていない条件は、推測で決めず、実装と実データを確認して合意のうえで確定する。

## 9. リスク・解釈上の注意

- OIは未決済建玉の総数であり、OIだけから買い手・売り手のどちらが主導したかを断定できない。
- 価格とOIの組合せは需給の手掛かりだが、単独で参加者の意図を証明しない。
- オプションのストライク別OIは建玉集中を示すが、参加者別のネットポジションやディーラーのガンマ方向を直接示すものではない。
- GLDオプションをGC価格に換算する場合、商品間の価格関係を利用した近似として扱い、GCオプションと無条件に合算しない。
- データの公表時刻・遅延・欠損・限月交代を考慮し、異なる時点のデータを同時点の情報として扱わない。
- 分析結果は確率的な判断材料であり、将来の価格や利益を保証しない。

## 10. 開発の進め方

1. 現在のPR・実装・テスト結果を確認する。
2. PG62／PG64の実PDF検証に必要なケースと合格条件を確定する。
3. 不足しているテストを追加し、実PDF照合を実施する。
4. 抽出品質が確認できた後、履歴更新の安全性を検証する。
5. 履歴データから公開Webアプリまでのデータ経路を確認する。
6. PG64マスター生成とオプション派生データの縦断スライスを作り、その後PG62等の限月別データ、中心限月判定、連続チャートを段階的に接続する。
7. 基本的な先物データの表示を安定させてから、COT・ETF・ロコ・ロンドン・フロー分析を順次追加する。
