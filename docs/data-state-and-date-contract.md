# データ状態遷移と日付定義（設計案）

> 状態：提案中（未実装・未検証）  
> 目的：PDFの版管理、抽出・検証・公開の判定、時系列結合の意味を明示し、未確認のデータを誤って売買分析・公開へ流さない。

## 1. 基本原則

1. **原本の版状態、処理状態、公開可否は別の軸として管理する。** ひとつの巨大な status enum に異なる意味を混在させない。
2. 未知・不一致・未確認は欠損値やゼロに変換せず、隔離または未解決として保持する。
3. 状態の昇格は明示的な条件と監査記録を必要とする。再実行で過去の判定を黙って上書きしない。
4. 数値と符号の正確性に許容差は設けない。網羅率・隔離率などの運用指標は別途、実PDF検証に基づいて閾値を決める。
5. この文書は設計案であり、現行パーサーがこれらを実装していることを意味しない。

## 2. 状態を3軸に分離する

### 2.1 原本リビジョン状態（source_revision_status）

同じbulletin dateでも複数ファイルが存在し得るため、日付ではなく原本ファイルのSHA-256を識別子とする。

| 状態 | 意味 |
|---|---|
| `UNCLASSIFIED` | PRELIMINARY / FINAL 等の版種を確認できていない |
| `PRELIMINARY` | 原本に速報版であることを示す明示情報がある |
| `FINAL` | 原本に確定版であることを示す明示情報がある |
| `REVISED` | 訂正版であることを示す明示情報がある |
| `CONFLICTING_EVIDENCE` | 原本表示・取得履歴に矛盾がある |

版種は推測で割り当てない。ファイル名や取得時刻だけでFINALに昇格させない。同一日付で別SHA-256を検出したら、両方を保存・記録し、差分を確認する。旧版を削除・上書きしない。PRELIMINARYとFINALは同一bulletin dateの異なるリビジョンとして扱い、ファイルハッシュで区別する。REVISED等の版種が明示されている場合も別リビジョンとして保持する。

### 2.1.1 PRELIMINARY／FINALの保存・採用ポリシー

- **取得・内部保管**：権利・利用条件の確認範囲内で、PRELIMINARYとFINALの両方を取得候補にする。両方とも原本SHA-256、取得元、`retrieved_at`、原本上の版種表示、取得履歴を持つ独立したリビジョンとして記録する。公開リポジトリへの原本保存はライセンス確認が終わるまで行わない。
- **通常履歴の採用**：通常の履歴・Web分析向けビューは、原則としてFINALを採用する。ただしFINALであることだけでは不十分で、必要な抽出検証とデータ品質ゲートを通過していることを条件とする。
- **PRELIMINARYの用途**：速報値を明示的に調べる診断・比較・速報分析用の別ビューでのみ利用する。通常のFINAL履歴へ黙って混ぜない。
- **FINAL未着**：FINALが未発見・未取得・未検証の場合、PRELIMINARYを自動でFINALの代用品にしない。通常履歴は欠損／保留を示し、速報値を使う場合は利用者が選択できる別モードにする。
- **両版の差分**：同じbulletin dateのPRELIMINARYとFINALを比較できるようにし、値の差分、追加・削除行、ステータス、比較対象のSHA-256、比較ルール版を記録する。異なる意味の日付や契約キーを推測で揃えない。
- **同日複数版**：FINALが複数見つかった場合も自動で最終版を決め打ちせず、REVISED表示・公表情報・SHA-256・取得履歴に基づき判定し、曖昧なら隔離する。
- **過去履歴**：既存データがPRELIMINARYかFINALか判別できない場合、内容やファイル名から推測してラベル付けしない。`UNCLASSIFIED` として記録し、出典PDFとの照合が済むまで通常のFINAL履歴として承認しない。

### 2.2 処理状態（processing_status）

| 状態 | 意味・次への条件 |
|---|---|
| `DISCOVERED` | URL等の取得候補を発見した |
| `QUARANTINED` | 取得失敗、権利確認待ち、版種不明、ハッシュ不整合等で通常経路から隔離 |
| `RAW_STORED` | 原本を保存し、SHA-256・取得時刻・取得元を記録した |
| `EXTRACTED` | 全ページの抽出結果と抽出証跡を保存した。正確性の承認を意味しない |
| `VALIDATION_FAILED` | 必須検査に失敗。派生・公開への昇格は禁止 |
| `VALIDATED` | 対象レイアウト・対象データの検証基準を満たした |
| `DERIVED` | バージョン付き規則により派生データを生成し、元レコード参照を保持した |
| `RETIRED` | 通常配信から退役。履歴・監査データは削除しない |

失敗後の再試行は同じ原本SHA・同じ処理バージョンなら再現可能であることを確認する。パーサーや規則の変更時は新しい実行記録を作り、以前の結果を残す。

### 2.3 公開状態（publication_status）

| 状態 | 意味 |
|---|---|
| `NOT_REVIEWED` | 公開審査前 |
| `BLOCKED` | ライセンス、検証、セキュリティ、品質等の未解決事項がある |
| `INTERNAL_ONLY` | 内部検証のみ。公開サイト・公開リポジトリへ配信しない |
| `APPROVED` | 対象のデータ種別・用途・配信先について明示的に承認済み |
| `PUBLISHED` | 承認済みの成果物を公開した |
| `WITHDRAWN` | 公開を取り下げた。理由と対象版を記録する |

公開可否はPDF単位だけでなく、**原本、抽出トークン、正規化データ、分析結果、シナリオ文面、配信先**ごとに記録する。CME等の権利確認が済むまで、原本PDFや派生データを公開しない。一般的な免責文だけでライセンス・規制上の問題が解決したとはみなさない。

### 2.4 状態の関係

- `FINAL` は原本の版種であり、`VALIDATED` や `APPROVED` を意味しない。
- `VALIDATED` は抽出・データ品質の検証結果であり、公開権限を意味しない。
- `DERIVED` は派生物の生成成功を意味し、投資判断への妥当性を保証しない。
- `BLOCKED_DIAGNOSTIC_ONLY` は複数の意味が混ざるため、正式な状態値としては新規利用しない。既存箇所は移行時に処理状態・公開状態・利用目的へ分解する。
- `parse_status` はセル／値単位の解釈結果（例：`PARSED`, `UNRESOLVED`, `NOT_APPLICABLE`, `INVALID`）に限定する。`row_status` は行単位の構造検査結果に限定する。いずれも文書全体の公開状態を代替しない。
- 遷移記録には `from`, `to`, `changed_at`, `actor`, `reason`, `rule_version` を保存する。自動処理の場合も actor を機械実行として記録する。

## 3. 日付と時点の契約

すべての日付・時刻は名称と意味を分け、曖昧な `date` フィールドを使わない。日付のみの値と時刻付きの値も区別する。

| フィールド | 意味 | 用途・注意 |
|---|---|---|
| `bulletin_date` | bulletin表紙・見出しが示す日付 | 原本識別の一要素。取引日と同一とは限らない |
| `trading_date` | 対象市場の取引セッション日 | 取引カレンダーとセッション定義に基づく |
| `publication_at` | 当該版が公表された時刻（分かる場合） | タイムゾーンを保持。日付しか分からなければ時刻を捏造しない |
| `retrieved_at` | システムが原本を取得した時刻 | 取得運用の監査用。公表時刻の代用にしない |
| `observation_date` | 数値が観測・集計対象とする日付 | 各項目の定義に従う。行全体に一律で当てはめない |
| `open_interest_as_of` | OI値が有効な基準日 | Bulletinの日付から機械的に推測しない。明示見出し・仕様で確認する |
| `expiry_date` | 契約仕様で定義された満期日 | 出典と仕様バージョンを記録する |
| `delivery_date` / `last_trade_date` | 受渡し日／最終取引日 | 商品仕様・カレンダーの出典を記録し、満期と混同しない |
| `known_at` | その情報がシステムで利用可能になった時点 | point-in-time再現・先読み防止に使う |
| `as_of` | 分析が情報を参照できる締切時点 | バックテストでは `known_at <= as_of` を満たすデータだけを使う |

### 3.1 時刻・タイムゾーン

- 時刻付きイベントは元のタイムゾーンとUTC換算を保持する。元時刻が不明な場合、UTC時刻を推定しない。
- 日付だけの値は日付型として保存し、深夜UTCのタイムスタンプに擬装しない。
- `known_at` は取得時刻と同一とは限らない。過去データを後日一括取得した場合、当時から利用可能だったと見なしてはならない。歴史的な公表時刻が不明なら不明と記録する。

### 3.2 OI・価格・契約データの結合

- Bulletin dateだけをキーに、価格・出来高・OIを無条件に結合しない。
- 価格・出来高・OIはそれぞれ観測対象日を持ち、OIは原本が示す基準日・報告慣行を確認してから結合する。
- PG62とPG64の結合には、日付だけでなく、明示的に検証された商品コード／契約識別子対応と対象原資産限月を必要とする。対応が確定できないシリアル／週次オプションは `UNRESOLVED` のまま隔離する。
- `bulletin_date`、`trading_date`、`open_interest_as_of` の変換規則は、出典・根拠・ルールバージョン付きで管理する。暗黙の「前営業日」補正は禁止する。

## 4. point-in-time履歴と訂正

- 原本・抽出結果・正規化結果・分析結果は、生成時点の版を追記保存し、既存結果を上書きしない。
- 各レコードは少なくとも `source_sha256`、`parser_version`、`schema_version`、`rule_version`、`known_at`、`source_record_ref` を持つ。環境再現に必要な依存ロックファイルのハッシュ、実行環境情報も実行マニフェストに記録する。
- 訂正版が来た場合、訂正版の原本と派生結果を追加する。最新状態のビューは作ってよいが、過去の `as_of` 時点で知られていた値を再構築できなければならない。
- バックテストは、各意思決定時点の `as_of` より後に `known_at` となった訂正・データを使わない。

## 5. 受け入れ条件（案）

実装前に閾値・承認者を確定する。以下は測定項目の定義であり、未検証の数値を合格基準として捏造しない。

- **数値・符号一致率**：独立に確認した必須フィールドで、原本との値・符号が完全一致した割合。許容差はゼロ。不一致が1件でもあれば対象レコードを隔離し、重大項目の不一致はリリースを停止する。
- **構造網羅率**：対象PDFのページ・対象セクション・対象行・必須列のうち、検出・記録できた割合。分母は独立した参照目録で定義する。
- **隔離率**：対象レコードのうち、未解決・不一致等で隔離した割合。隔離率が低いだけでは正確性を証明しない。高い場合も、未解決を無理に自動解釈しない。
- **合計照合**：行数・行合計・TOTAL等は補助的な整合性検査として使用する。合計一致だけで正確性を認定しない。
- **承認責任**：基準値と変更履歴は文書化し、実装者以外のレビューを含めて承認する。閾値未決定の間は診断専用とし、公開・売買シグナル用途へ昇格させない。

## 6. 未決事項

1. CME原本・抽出トークン・派生データ・分析文面それぞれのライセンスと公開条件。
2. PG62／PG64の公式商品・限月対応表、およびシリアル／週次オプションの原資産限月決定根拠。
3. PRELIMINARY／FINAL／REVISEDの原本上の判定根拠と、昇格承認者。速報版と確定版の比較を通常履歴からどう分離して表示するか。
4. 複数の実PDF日付・レイアウトを使った網羅率・隔離率の数値基準と停止条件。
5. タイムゾーン、取引カレンダー、OI基準日、満期・受渡し関連日の公式出典。
6. 既存 `cme-gc-history.json` をどの派生層へ移行するか、互換ビューとロールバック方式。
7. Web配信データの形式・容量上限・公開審査とアクセス制御。
