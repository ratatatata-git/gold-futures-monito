## 0. 文書の読み方と確定度

要件を次の4種類に区別する。

- **MUST（必須）**：安全性、正確性、監査可能性のために守る。
- **SHOULD（推奨）**：合理的な理由と記録がない限り採用する。
- **PROPOSED（提案）**：設計案。実PDF・実装・運用で検証し、正式採用を決める。
- **OPEN（未決）**：根拠や承認が不足している。AIや実装者が独断で確定してはならない。

「目標」「仕様」「実装済み」「検証済み」「公開承認済み」は別の概念である。ドキュメント、テスト、コードが存在するだけでは、実データの正確性や本番適合性を証明しない。

## 1. エグゼクティブ・サマリー

Gold Futures Monitor は、COMEX金先物（主にGC）と関連オプションを中心に、ファンダメンタルズ、価格・出来高・建玉（Open Interest; OI）、参加者ポジショニング、オプション構造、トレンド追随フローの仮説を統合し、デイトレード／スイングトレードの判断材料を提供する分析システムである。

本システムは自動売買執行を行わない。観測された事実、決定的な計算値、仮定を含む推定値、分析シナリオを明示的に分離する。

開発の優先順位は次のとおり。

1. ソースの権利・出典・版種を管理する。
2. PG62（先物）／PG64（オプション）の実PDFから、raw token、符号、列、行、商品、限月、日付を正確に抽出する。
3. 原本・抽出マスター・正規化データ・分析データ・配信用データを分離し、再現可能にする。
4. 検証に合格したデータのみ履歴と本番画面へ反映する。
5. 先物・COT・オプション・ファンダメンタルズを統合した分析を、仮説検証とバックテストを経て追加する。
6. 監視・障害対応・ロールバック・権利審査を含む運用を確立する。

**品質ゲートを通過していないデータを、欠損補完や推測によって「完成データ」に見せてはならない。** 未解決状態を維持して隔離することは、正常な処理結果である。

## 2. 目的・利用者・利用範囲

### 2.1 目的

- **ファンダメンタルズ**：金価格の中長期的な方向性に影響する要因を整理する。
- **先物ポジショニング**：価格変化とOI変化、限月間の出来高／OI移行から、ポジション形成・解消の可能性を整理する。
- **参加者ポジション**：CFTC COT等を用い、報告参加者区分別の週次ポジションと極端値を把握する。
- **オプション構造**：満期・CALL/PUT・ストライク別OI、出来高、IV等を可視化し、建玉集中と潜在的なヘッジ圧力を検討する。
- **フロー仮説**：CTA／トレンド追随戦略やディーラーヘッジに関連する価格帯・条件を推定する。
- **統合シナリオ**：ファンダメンタルズ、モメンタム、ポジショニング、オプション構造の一致・不一致を整理し、条件付きシナリオを提示する。

### 2.2 利用者と想定用途

- 主利用者：開発・分析を行うプロジェクトオーナー。
- 将来の利用者：公開または限定公開のWebアプリ利用者（権利・配信条件が確認された範囲に限る）。
- 用途：市場状況の把握、仮説形成、検証、トレード判断の補助。
- 非用途：自動注文執行、利益保証、確実な将来価格予測、根拠不明な「スマートマネー」の断定。

### 2.3 成功条件

1. 原本の版と取得時点が追跡できる。
2. 抽出された各値から、原本の該当ページ／表／行／セルまたはトークンへ遡れる。
3. 実PDFで独立確認した値・符号が完全一致する。数値や符号の許容誤差はゼロとする。
4. 未解決・異常・版種不明のデータが本番履歴へ黙って混入しない。
5. 同一入力・同一コード・同一設定で再現できる。
6. 過去時点で利用可能だった情報だけを使う分析・バックテストができる。
7. 公開前にデータ権利、公開範囲、品質ゲート、ロールバック手順が承認されている。
8. 分析結果は出典、計算式、仮定、制約、更新時点を説明できる。

## 3. スコープ

### 3.1 対象

- CME Daily Bulletin PG62等の金先物データ（実際に掲載されている価格、出来高、OI、OI変化、契約情報）。
- CME Daily Bulletin PG64等の金オプションデータ（PDFに掲載された商品、CALL/PUT、満期、ストライク、OI、出来高、IVその他確認済み項目）。
- CFTC COT等の参加者ポジションデータ。
- 金市場のファンダメンタルズ関連データ（採用元・頻度・権利を個別審査）。
- 将来的なETF保有量、ロンドン市場の保有・残高、GLDオプション等。ただしデータ源、権利、商品間マッピング、更新頻度が確定するまでは未確定スコープ。
- ブラウザで利用するWebアプリ／PWAと、その配信用派生データ。
- CI、データ取込、検証、リリース、監視、障害復旧の運用。

### 3.2 非対象・明示的制約

- 自動売買・ブローカー注文執行は対象外。
- PG64からGC先物のOHLC／OIを推測しない。先物の契約別データはPG62等の確認済みソースを用いる。
- OIだけで参加者の売買方向、ディーラーのネットガンマ、CTAの実ポジションを断定しない。
- CMEの原本PDF・抽出値・派生データの公開権限は未確認。免責文だけで権利問題が解決したとみなさない。
- 合成データテストだけで実PDFの正確性を認定しない。
- 「FINAL」であることと、抽出の正確性・公開承認・分析妥当性を同一視しない。

## 6. ソースと版管理

### 6.1 Source Manifest

原本ごとに最低限、次の情報を保持する。

- `source_id`：システム内の安定した識別子。
- `source_provider`、`source_document_type`：提供元と資料種別（例：CME、PG62／PG64）。
- `source_url`：実際に取得したURL。利用規約・アクセス制限を遵守する。
- `original_filename`、`sha256`、`byte_size`、`page_count`。
- `bulletin_date`、`bulletin_number`（存在する場合）、`edition_status`。
- `publication_at`、`retrieved_at`、`known_at`（分かる範囲で。未知を捏造しない）。
- `rights_status`、`allowed_uses`、`publication_status`。
- `parser_version`、`schema_version`、`rule_version`、実行環境マニフェストへの参照。

ファイル名は補助情報であり、原本同一性の根拠はSHA-256と原本内の明示情報を組み合わせる。ファイル名の日付とPDF記載の日付が異なる場合は警告・隔離し、自動的にどちらかへ寄せない。

### 6.2 PRELIMINARY / FINAL / REVISED

- PRELIMINARYとFINALは、同じbulletin dateであっても別の原本リビジョンとして保存・識別する。
- 各版はSHA-256、source URL、取得時刻、印字された版種・版番号等の証拠を持つ。
- 通常の履歴・Web分析では、**FINALであることが確認され、抽出検証にも合格したデータのみ**を採用する。
- PRELIMINARYは速報・診断・差分比較の明示モードでのみ利用できる。通常履歴に自動混入させない。
- FINALが未取得、未検証、または抽出失敗の場合、PRELIMINARYで黙って穴埋めしない。通常履歴は欠落／保留として表示する。
- PRELIMINARYとFINALの比較では、追加・削除行、値の変更、変更不能なマッピングを分けて記録する。行の対応が確定しない場合は推測で差分を結ばない。
- 同一日付に複数のFINAL候補がある場合、取得時刻だけで最新を自動採用しない。原本上の訂正・版情報等の証拠を調査し、曖昧なら隔離する。
- 旧データで版種を確認できない場合は `UNCLASSIFIED` とする。過去のファイル名や現在の期待だけでFINALへ昇格させない。
- 版種、抽出状態、公開状態は独立軸であり、FINALはVALIDATED／APPROVEDを意味しない。

### 6.3 権利と公開

公開状態の既定値はブロックとする。権利確認前は、原本PDF、raw extraction、正規化データ、派生データを公開Webへ配信しない。CME等の規約・ライセンスは、原本、抽出、派生、表示、再配布ごとに確認する。必要なら非公開ストレージまたはローカル環境に分離する。

## 7. データ状態・日付・履歴契約

詳細な正本は [データ状態遷移と日付定義](data-state-and-date-contract.md) を参照。本節は全モジュール共通の要約である。

### 7.1 状態軸

- `source_revision_status`：`UNCLASSIFIED` / `PRELIMINARY` / `FINAL` / `REVISED` / `CONFLICTING_EVIDENCE`
- `processing_status`：`DISCOVERED` / `QUARANTINED` / `RAW_STORED` / `EXTRACTED` / `VALIDATION_FAILED` / `VALIDATED` / `DERIVED` / `RETIRED`
- `publication_status`：`NOT_REVIEWED` / `BLOCKED` / `INTERNAL_ONLY` / `APPROVED` / `PUBLISHED` / `WITHDRAWN`
- `parse_status`：セル／値の解釈状態。例：`PARSED` / `UNRESOLVED` / `NOT_APPLICABLE` / `INVALID`
- `row_status`：行構造の検査状態。文書の公開状態の代替にはしない。

状態変更は `from`、`to`、`changed_at`、`actor`、`reason`、`rule_version` を記録する。自動処理もactorを記録する。状態遷移を上書きで消さず履歴として残す。

### 7.2 日付の意味

曖昧な単一の `date` を使わず、必要に応じて以下を区別する。

- `bulletin_date`：Bulletinに記載された日付。
- `trading_date`：市場セッションの取引日。
- `publication_at`：公表時刻。
- `retrieved_at`：システム取得時刻。
- `observation_date`：値が観測対象とする日付。
- `open_interest_as_of`：OI値の基準日。
- `expiry_date`、`last_trade_date`、`delivery_date`：契約仕様に基づく各日付。
- `known_at`：情報がシステムで利用可能になった時点。
- `as_of`：分析が参照できる情報の締切時点。

日付だけの値を根拠なくUTCタイムスタンプへ変換しない。タイムゾーン・取引カレンダー・休日の扱いは、採用する公式出典とバージョンを記録する。

### 7.3 Point-in-timeと訂正

原本、抽出、正規化、分析結果は追記保存し、既存版を黙って上書きしない。各派生レコードは入力ソース参照、入力SHA、コード／ルール／スキーマバージョン、`known_at` を持つ。過去の `as_of` 分析では `known_at <= as_of` を満たす情報のみ使用する。後日取得した履歴データを、当時から利用可能だったとみなしてはならない。

## 8. PDF抽出仕様（PG62 / PG64）

### 8.1 共通ルール

1. 原本を変更せず保存し、SHA-256を計算する。
2. PDF内の日付、版種、文書種別、ページ数、商品／セクション見出しを確認する。
3. ページ単位でraw text/token、必要な文字単位の位置情報、ページ番号を保存する。
4. 明示された見出し・セクション境界・列見出しを用い、ページ内で表構造を復元する。
5. 座標は行／列所属の証拠として利用するが、絶対座標、固定行数、ページ番号、限月順序を意味の唯一の根拠にしない。
6. 商品、限月、CALL/PUT、満期、ストライク、項目の意味が確定しない場合は未解決とする。
7. raw tokenとnormalized valueを分離し、変換根拠・ルールバージョンを保存する。
8. 異常・欠落・重複・未知ヘッダー・列ずれ・TOTAL不一致候補を報告する。
9. 独立確認した実PDF fixtureと比較し、ページ／セクション／行／必須列の網羅性を評価する。
10. 新しいレイアウトに未対応の場合、正常終了を装わず失敗または隔離する。

### 8.2 特殊値

次の表現を同じ状態に潰してはならない。

- 数値 `0`
- 空欄／欠損
- `----`
- `UNCH`
- 符号付き数値・変化量
- `B/A`等の複合表記
- 抽出不能／文字化け／曖昧なトークン

raw tokenは原資料の文字列を保持する。正規化は検証済みの規則がある場合に限る。複合値を都合よく単一数値へ分割しない。数値、符号、列の対応は完全一致を要求する。

### 8.3 PG62の責務

PG62等の確認済み先物資料から、取引日・商品・限月ごとに、実際に掲載されたOpen、High、Low、Settlement／Close、Volume、OI、OI Change等を正規化する。項目名と意味は実際の見出しと資料仕様で確定する。PNT/PIT等の内訳は、原本の項目定義を確認して保持し、根拠なく合算・省略しない。

### 8.4 PG64の責務

PG64はオプションデータのソースとして扱う。全ページ／全セクション／全表の抽出証拠を持つマスターを作り、その後で用途別のOptions Normalizedを派生させる。PG64をGC先物のOHLC／OIの代用にしない。商品・満期・CALL/PUT・ストライク・列の対応が未解決なら、正規化・分析に流さない。

### 8.5 実PDF検証セット

合成データだけでなく、少なくとも次の特徴を持つ実PDFを組み合わせる。

- PRELIMINARYとFINALの両版がある日付。
- 通常日と休日・短縮週周辺。
- 行数／商品数／限月構成が異なる日付。
- 桁数、符号、B/A等の複合値、空欄・特殊値が現れる日付。
- ページ構成・レイアウトが異なる版。
- 満期集中日、週次／シリアルオプション等、契約マッピングが難しいケース。

各fixtureには原本SHA、対象ページ、独立転記者／確認者、照合範囲、確認日、パーサー／ルールバージョンを記録する。テストに使うPDFの公開・リポジトリ保管も権利確認の対象である。

## 9. 正規化・結合・商品マスター

### 9.1 正規化レコードの共通属性

各レコードには、可能な範囲で次を保持する。

- 一意のrecord IDまたは安定した自然キー。
- ソースID、source SHA-256、ページ／表／行／セル参照。
- bulletin／trading／observation／OI基準日など、意味が明確な日付。
- 商品コード、限月コード、契約識別子。
- raw token、normalized value、value type、parse status、issues。
- schema／parser／rule version、`known_at`、生成時刻。
- validation status、quarantine reason、承認履歴。

### 9.2 商品・限月マッピング

商品コード、別名、満期、原資産限月の対応はバージョン付きマスターで管理する。名称の部分一致や近似文字列だけで自動結合しない。対応ルールには根拠ソース、適用範囲、有効期間、レビュー状態を付ける。商品マスターが未解決なら、そのレコードを未解決のまま残す。

PG62とPG64の結合は、日付だけでは行わない。商品・契約・OI基準日・原資産限月のマッピングが確認できる場合に限る。週次／シリアルオプションで原資産先物限月を確定できない場合は `UNRESOLVED` とし、分析に混ぜない。

### 9.3 重複・訂正

同じソースSHAの再処理と、同じ日付の別版・訂正版を区別する。同一入力の再実行で重複データを作らない。異なるSHAは別の原本候補として保持し、内容が同じように見えても自動的に捨てない。

## 10. 派生データと分析モデル

### 10.1 Contract Daily（先物）

PG62等から、契約別の価格・出来高・OIを保存する。市場全体のOIと単一限月のOIを混同しない。OI変化は原本掲載値と、システムが前日差から計算した値を区別する。計算値は式・入力・基準日を保存する。

### 10.2 中心限月判定（Active Contract）

中心限月判定は独立した派生レイヤーとする。日付ごとに選択限月、候補限月、出来高、OI、契約期限条件、判定理由、rule version、入力参照、警告、解決状態を保存する。

出来高最大だけで確定しない。出来高とOIの移行、複数日にわたる持続性、満期・受渡し・最終取引日の制約などを実データで評価する。ルールが未確定、または候補が拮抗している場合は未解決にする。後からルールを変更しても過去の判定履歴を追跡可能にする。

### 10.3 連続先物系列（Continuous Series）

- 未調整の限月別実価格を保持する。
- ロール日、旧限月、新限月、価格差、選択理由、入力判定IDを記録する。
- 調整済み価格を作る場合は、調整方式（例：未調整、差分調整、比率調整）を明示し、実価格とは別フィールド／別系列にする。
- 出来高・OIは価格と同じ方法で調整しない。
- ロールによる価格差を実市場の当日変動と誤認させない。
- ロールルール変更時は全履歴を再生成し、旧版との差分を監査する。

### 10.4 価格変化 × OI変化

価格とOIの増減は、需給の仮説を整理するためのヒューリスティックとして利用する。典型的な読み方（価格上昇＋OI増加＝新規ポジション形成の可能性等）は確定的な参加者識別ではない。価格・OIの時間軸、契約間移動、ロール、報告タイミングを考慮し、確信度と代替解釈を表示する。原データと解釈ラベルを同じフィールドに上書きしない。

### 10.5 COT

- レポート種別、参加者区分、ロング／ショート／スプレッド等、ネット計算式、報告基準日、公表日を明示する。
- 週次データであり、日中のポジションと誤認させない。
- ネットポジション、過去分布に対するパーセンタイル等は派生値として、窓長・式・データ版を記録する。
- 改訂や分類変更、データ取得時点を追跡する。
- 公表時刻をまたぐバックテストでは、当時利用可能だった情報だけを使用する。

### 10.6 オプションOI・IV・集中帯

- 満期、CALL/PUT、ストライク、商品／原資産対応、OI、出来高、IV等の各項目を表示する。
- OI集中帯は集計範囲、契約対象、満期範囲、計算式を明示する。総OIと日次変化、CALLとPUTを不用意に合算しない。
- 集中価格帯は、将来のサポート／レジスタンスを保証しない。「建玉集中」と「価格が反応する水準」は異なる概念として扱う。
- OI・IVが前日基準の場合、UIに基準日を表示する。
- 商品や満期が未解決のオプションは集中帯・ガンマ計算から除外し、除外件数を報告する。

### 10.7 ガンマ関連推定

- 原資料にディーラーのネットポジションが直接掲載されているとは仮定しない。
- OIだけからディーラーの買い／売りガンマを確定できないことを明示する。
- 推定する場合は、符号仮定、顧客ポジション仮定、IV、金利、満期、原資産価格、オプション種別、倍率、計算モデル、データ基準時刻を記録する。
- ギリシャ指標の数式と単位をテストし、境界条件・満期近辺・低流動性・欠損IVの挙動を確認する。
- 「推定GEX」「想定ディーラーヘッジ」等と表示し、実測値と区別する。
- 検証計画がない段階では診断・研究用途にとどめ、確定シグナルとして公開しない。

### 10.8 CTA／トレンド追随フロー推定

CTAフローは直接観測値ではなくモデル推定である。使用する価格系列、ボラティリティ、トレンド指標、ルックバック、リスク配分、閾値、ポジション上限、データ基準時刻を記録する。パラメータは後付けで将来の値に合わせない。ウォークフォワード／アウト・オブ・サンプル検証、感度分析、偽陽性／偽陰性の評価を行い、実際のCTA保有ポジションと誤認させない。

### 10.9 ファンダメンタルズと統合シナリオ

各要因は出典、観測値、発表時刻、既知時刻、更新頻度、単位、改訂可能性を持つ。統合シナリオは「事実」「計算」「推定」「仮定」を分け、シナリオ条件、支持材料、反証条件、無効化条件、対象期間、データ不足を示す。複数指標が同方向だからといって、独立した証拠として単純加算しない。バックテストと実運用の成績は分け、将来情報の漏洩を防ぐ。

### 10.10 将来候補ソース（ETF／ロンドン市場／GLD）

GLD保有量、ロンドン市場の保有・残高、GLDオプションなどは有用な候補だが、採用前に以下を確定する。

1. 公式または信頼できるソースと利用規約。
2. 公表頻度・公表時刻・履歴改訂。
3. 単位、通貨、重量、対象資産の定義。
4. GC先物・COMEXオプションとの対応関係（単純な1対1関係と仮定しない）。
5. 欠損・休場・遅延時の扱い。
6. point-in-timeバックテストに必要な `known_at`。
7. 公開可否と引用／再配布条件。


### 10.11 CFTC COT・FREDマクロ系列の自動取得（設計提案／未検証）

**状態：取得方式の候補はあるが、実環境での取得・列検証・履歴更新は未完了。** APIやCSV URLが存在することと、正しい金市場データを安全に自動取得できることは別の合格条件である。以下の識別子やURLは、実装前に公式メタデータと実データで再確認する。

#### CFTC COT

- 候補ソース：CFTC Public Reporting Environment の公式データセット／API。COTは通常、火曜日時点のポジションを金曜日に公表する週次データだが、祝日等による遅延を許容し、固定曜日だけで欠損判定しない。
- 提示された `72hh-3qpy` は **Disaggregated Futures Only** として識別されており、Futures-and-Options Combined として扱ってはならない。
- `gqe8-fqbz` と `6dca-aqww` は、採用するレポート種別・金市場レコードを満たすことを公式メタデータと実データで確認するまで確定ソースIDにしない。Combined の候補IDとして `kh3c-gbw2` が挙がっているが、公式のデータセット情報と列定義を照合するまで未確認候補にとどめる。
- 実装前に、各データセットの正式タイトル、レポート種別（Disaggregated／Legacy、Futures Only／Futures-and-Options Combined）、市場名、取引所／市場コード、列名・型・単位、更新履歴、API制限を記録する。
- 金市場の行は `GOLD` の文字列一致だけで選ばない。正式な市場名・取引所・契約市場コードなど、公式メタデータで確認した識別条件を使い、条件が競合した場合は隔離する。
- 最低限、`report_date`（火曜日時点）、`publication_at`（公表時刻が確認できる場合）、`retrieved_at`、`known_at`、`source_dataset_id`、`source_revision`、レポート種別、参加者区分、Long／Short／Spreading、元の値を保持する。公表日をポジション基準日として代用しない。
- 取得は再実行安全とし、再取得・訂正を黙って上書きしない。重複キー、必須列欠落、型変更、件数急変、最終観測の遅延を検査し、失敗時は直近の承認済みデータを維持して新規データを隔離する。
- 週次取得は金曜日以降のスケジュールに加え、遅延時の再試行と手動再実行を備える。成功したジョブ実行をデータ正確性の証明としない。

#### FRED・金利・ドル系列

- `DGS10` は米国10年国債利回り系列の候補とする。FREDのグラフCSV URL（例：`https://fred.stlouisfed.org/graph/fredgraph.csv?id=DGS10`）または公式APIのいずれかを採用する前に、GitHub Actions等の実行環境でHTTP取得、文字コード、列名、日付、欠損表現、最新観測日を実測する。
- FRED APIを使う場合はAPIキーをGitHub Secrets等のシークレット管理に置き、リポジトリへ保存しない。APIキーの必要性、利用条件、リクエスト制限を実装時に確認する。
- `observation_date`、値、欠損状態、`retrieved_at`、`known_at`、系列ID、取得方法、原レスポンスのSHA-256、処理バージョンを記録する。休日や非営業日の欠損をゼロに変換したり、前値で自動補完したりしない。補完を分析で行う場合は、別の派生列として方法と許容期間を明示する。
- 系列改訂や遡及変更を考慮し、取得版と改訂履歴を追跡できるようにする。バックテストでは当時取得可能だった値だけを使う。
- ICE DXY（ドル指数）とFREDの広義ドル指数（例：`DTWEXBGS`）は別の系列であり、互換の別名として扱わない。`^TNX` は別プロバイダーのティッカーであり、FRED系列IDではない。採用する系列ごとに定義・単位・出典・権利を記録する。

#### 自動取得の受け入れ条件

1. 実際のCI／運用環境から少量のデータを取得し、HTTPステータス・レスポンス形式・列・型を確認する。
2. 独立に公式ページ／メタデータと照合した金市場レコード、基準日、値を含むfixtureを作る。
3. 欠損、遅延、休日、列変更、重複、訂正、空レスポンス、レート制限、通信障害のテストを通す。
4. 同じ入力を再実行しても重複・不必要な差分が生じず、訂正は別版として追跡できる。
5. 権利審査と公開承認が済むまでは内部用途に限定し、公開用データの生成・配信をブロックする。

### 10.12 金ETF保有量（GLD等）とLBMAロンドン保管残高

**状態：採用候補。自動取得経路、履歴完全性、再配布条件は未確認。** 「取得可能なページがある」「日次／月次で公表される」と「安定した公式APIや許諾済み自動フィードがある」を区別する。スクレイピングは第一選択にせず、公式のダウンロード／フィード、利用規約、機械取得の可否を先に確認する。

#### GLDおよびその他の金ETF

- まずSPDR Gold Shares（GLD）の発行体／公式商品ページ等、提供元が指定する公式ソースを優先して調査する。World Gold Council（WGC）の集計は対象ETF・国・頻度・公表遅延が個別ファンドのデータと異なる可能性があるため、GLDの日次残高の代替として無条件に混在させない。
- 保有金量（トロイオンス／トン）、評価額、AUM、株価、シェア数、フローは異なる指標として別フィールドにする。AUMや株価から保有金量を逆算しない。トン換算は採用した単位定義・換算定数を記録する。
- 各記録は少なくとも `fund_id`、`ticker`、`observation_date`、保有量、元の単位、正規化単位、`publication_at`（確認できる場合）、`retrieved_at`、`known_at`、source URL、原レスポンス／ファイルのSHA-256、データ版、検証状態を持つ。
- 公表が毎営業日と想定される場合でも、休日・更新遅延・訂正・空値を許容する。日付が異なる値を同一日として扱わず、前値補完は生データでは行わない。
- Yahoo Finance等の第三者サイトは、公式ソースや許諾されたデータAPIの代替として自動的に承認しない。利用規約、データ利用権、履歴範囲、更新保証を確認する。

#### LBMA Loco London保管残高

- LBMAが公表するロンドン貴金属保管庫の金保管残高を候補とするが、対象範囲・集計定義・発表日・ファイル形式・取得URL・再配布条件を公式資料で確認してから実装する。
- 月次データは日次データとして補間しない。観測対象月（例：月末時点）と実際の公表時刻／取得時刻を分離し、遅れて公表された値を公表前から既知だったものとしてバックテストに使わない。
- `observation_period` または `observation_date`、保管量、単位、対象金属、定義、`publication_at`、`retrieved_at`、`known_at`、source URL、SHA-256、版・改訂状態を記録する。
- PDF／Excel／HTMLのどの形式が安定して提供されるか、過去月の修正・再掲を検知できるか、ファイルの自動取得が利用条件に合致するかを検証する。PDF表抽出を使う場合は本仕様の抽出マスター・照合・隔離ルールを適用する。

#### 統合ルール

- COT（週次）、ETF保有量（日次を想定）、LBMA保管残高（月次）は観測頻度・公表遅延・対象範囲が異なる。単純に日付で結合せず、各系列の `observation_date/period` と `known_at` を保持する。
- ETF保有量はファンド保有、LBMA残高はロンドン保管庫における対象資産の集計であり、相互に独立した総量や同一母集団とは仮定しない。GLDがLBMA保管庫内に保管される可能性など、集計対象の重なりを検証せずに合算しない。
- これらはファンダメンタルズの説明変数・ダッシュボード項目候補であり、単独で金価格の方向や需給を断定する指標ではない。ラグ、改訂、定義変更、他指標との相関を記録し、バックテストではポイント・イン・タイムを守る。
- 権利・取得方式・単位・定義・履歴検証が確定するまで、公開配信を許可しない。取得できても公開利用権が確認できない場合は内部検証にとどめる。

## 11. 検証・テスト戦略

### 11.1 テスト層

1. **Unit tests**：トークン保持、数値パース、符号、行・列グルーピング、状態遷移、日付処理、計算式。
2. **Schema tests**：JSON Schema、必須フィールド、enum、型、キーの一意性。
3. **Fixture tests**：独立確認済みの実PDF抜粋に対する厳密一致。
4. **Real-PDF integration tests**：文書全体のページ・セクション・行・列・例外処理。
5. **Edition comparison tests**：PRELIMINARY／FINAL差分、版の非上書き、通常履歴の選択。
6. **History tests**：重複、訂正、再実行、差分、rollback、既存履歴保護。
7. **Analytics tests**：計算式、単位、境界条件、point-in-time、再現性。
8. **UI/E2E tests**：空状態、エラー、日付、契約、単位、データ鮮度、推定値の表示。
9. **Deployment tests**：CI、配信成果物、公開URL、キャッシュ／Service Worker、復旧。
10. **Operational tests**：欠損ソース、レイアウト変更、権利ブロック、失敗時停止、通知。

### 11.2 数値と符号の合格基準

- 重要な値・符号・キー・日付・契約マッピングは、独立確認した期待値と完全一致を要求する。許容差はゼロ。
- 一致しない値は隔離し、重大項目の不一致が残る状態でリリースしない。
- 網羅率の分母は、独立した参照目録（対象ページ・セクション・行・必須列）で定義する。
- 隔離率がゼロであることを合格条件にしない。未解決のまま正しく隔離する方が、誤った値を埋めるより望ましい。
- TOTALや行数の一致は補助的検査であり、個々の値の正確性の代わりにならない。
- 数値の閾値や網羅率基準は、複数の実PDFサンプルを計測してから承認する。未計測の基準を作り上げない。
- すべてのレコードが未解決でも「エラーなし」と判定されないよう、最低限の構造網羅率と必須項目解決率を設ける。

### 11.3 合成テストの限界

既存の合成データテスト（例：行グルーピング、raw token保持）は重要な単体テストだが、実PDFの全ページ精度を証明しない。実PDFと独立転記fixture、履歴更新、公開URLの確認を別々に通過させる。

## 12. 履歴更新とトランザクション

履歴更新は次の手順を守る。

1. 入力原本の版種・SHA・権利状態を検査する。
2. 原本を保存し、既存の版を上書きしない。
3. マスターを生成し、スキーマ検証を行う。
4. 実PDF照合・構造・値・契約マッピングを検証する。
5. 不合格なら隔離し、公開用履歴を変更しない。
6. 合格時に正規化・派生データを生成する。
7. 旧版と新しい成果物のキー、件数、主要値、差分を比較する。
8. FINALのみ通常履歴の候補とし、公開状態も承認済みであることを確認する。
9. ステージング成果物を検証してから公開先へ切り替える。
10. 実行ログ、入力ハッシュ、コード／依存関係、結果、承認、公開先を記録する。
11. 失敗時は直前の承認済み成果物へ戻せるようにする。

処理は再実行可能（idempotent）であること。途中失敗時に部分的な履歴更新や古い／新しいデータの混在を起こさない。生成物を一時領域で完成させ、検証後に切り替える方式を推奨する。

### 12.1 既存データの移行

既存の `data/cme-gc-history.json`、`data/cme-gold-options-history.json`、日付単位のJSON、マスターJSONは、現行の形式・利用箇所・版種・出典を棚卸しする。即時に削除・置換しない。旧データを移行する際は、版種不明を `UNCLASSIFIED` とし、検証済みFINALとして扱わない。互換ビュー、差分検証、ロールバック期間を設け、段階的に切り替える。

## 13. Webアプリ／PWA仕様

### 13.1 表示原則

- ページはデータの基準日、更新時刻、ソース、版種（必要な場合）、品質／確定状態を表示する。
- 価格、出来高、OI、OI変化、IV、パーセンタイル等の単位と意味を明示する。
- 欠損、未解決、ゼロ、ゼロ件、未取得、取得エラーを区別する。
- PRELIMINARYモードは明示的な選択と警告が必要。通常履歴に混ぜない。
- 推定指標は「推定」と表示し、仮定・対象期間・データ基準時刻への導線を持つ。
- データが古い／取得できない／検証不合格の場合、正常な最新データであるかのように表示しない。
- 過度に断定的な売買推奨文を避け、条件・反証・不確実性を表示する。

### 13.2 配信データ

Webアプリには、公開審査を通過した小さな派生成果物のみを配信する。マスター全体、内部診断ログ、未解決データ、権利未確認の原本をクライアントへ送らない。データ形式（JSON等）、分割、サイズ上限、キャッシュ戦略は実測と利用環境で決める。

### 13.3 PWA・キャッシュ

Service Workerのキャッシュは、古いデータを新しいものと誤認させないようにする。アプリコードとデータ成果物のバージョンを識別し、更新状態を表示する。公開後は通常読み込みとキャッシュ利用時の両方を確認する。データ取得失敗時に、キャッシュを表示する場合はその鮮度と基準時点を示す。

### 13.4 アクセシビリティ・使いやすさ

日付、契約、満期、CALL/PUT、単位、凡例を明確にする。色だけで方向や状態を示さず、テキストや記号も併用する。モバイル画面で表やチャートが読めること、空状態・エラー状態で次に必要な操作が分かることを確認する。

## 14. CI/CD・本番運用

### 14.1 パイプライン

推奨パイプライン：

```text
Source discovery / manual ingest
  -> rights + edition + SHA checks
  -> immutable raw archive
  -> extraction
  -> schema + unit tests
  -> real-PDF reconciliation
  -> quarantine / validation report
  -> normalized + derived build
  -> history diff + point-in-time checks
  -> publication approval gate
  -> staging artifact
  -> web/UI smoke tests
  -> publish
  -> post-deploy verification
  -> audit record
```

CIが成功したことと、データが正しいことは同義ではない。PDFのレイアウト変更を検知した場合、未知の構造を自動推測で通過させず、取込を停止してレビューを要求する。

### 14.2 監視指標

- ソース取得成功／失敗、取得遅延、想定版の未取得。
- SHA重複、同日複数版、FINAL候補の競合。
- ページ／セクション／行／列の網羅率。
- parse status別件数、隔離件数・率、重大エラー。
- 実PDF fixtureとの不一致数（値・符号・契約・日付）。
- 正規化／派生データ件数、キー重複、履歴差分。
- 公開成果物のSHA、サイズ、更新時刻、スキーマバージョン。
- Webアプリの読み込み失敗、JSON parse error、古いキャッシュ。
- 公開承認／権利状態と実際の配信成果物の一致。

### 14.3 障害時の対応

- **ソース未取得**：既存の承認済みデータを保持し、未取得を表示する。PRELIMINARYで代用しない。
- **版種不明／複数FINAL競合**：隔離して人手確認を求める。
- **抽出・スキーマ検証失敗**：本番更新を停止する。
- **実PDFとの不一致**：該当レコードと依存する派生データをブロックし、影響範囲を調査する。
- **権利問題の判明**：該当データの公開を停止し、対象成果物を特定して撤回・置換する。原本を無断で削除・改変せず、保管要件に従う。
- **Webデプロイ失敗**：前回の承認済み成果物へ戻し、公開先とキャッシュを確認する。
- **パーサーの重大バグ**：影響する入力SHAと生成物を列挙し、旧結果を消さず、修正バージョンで再生成して差分レビューする。

### 14.4 ロールバック

各リリースはコードコミット、配信データのSHA、スキーマ／パーサー／ルールバージョン、承認記録を紐付ける。ロールバックではコードだけでなく、配信データとキャッシュ状態も整合させる。ロールバック後に、公開URLでデータ鮮度と主要画面を確認する。

## 15. セキュリティ・権利・ガバナンス

- 認証情報、APIキー、Cookie、個人情報をGitへ保存しない。
- 公式サイトのアクセス制御・利用規約を回避しない。
- 取得頻度とアクセス方法は提供元の条件を守る。
- 依存関係を固定し、ロックファイルのハッシュと実行環境を記録する。
- 外部入力PDF／テキストは信頼できない入力として扱い、パーサーの例外・リソース消費・異常ファイルを検証する。
- 公開対象のデータ・コード・説明文はレビュー可能にし、公開前の承認記録を残す。
- データの利用権・保存権・派生物の権利・再配布権を混同しない。
- 投資判断に使う場合、推定値の不確実性、データ遅延、モデル限界を表示する。免責文は品質管理や権利確認の代わりにならない。

## 16. 開発・レビューの運用ルール

- 変更は小さな差分で行い、目的、影響ファイル、テスト、ロールバックを明示する。
- parser、schema、rule、source masterを変更したらバージョンを上げるか、変更履歴を記録する。
- 実データの変更とロジック変更を同じ差分に混在させないことを推奨する。
- テストの期待値は、パーサー出力から自動生成せず、原本から独立に確認する。
- 失敗したテストを削除・弱体化して通すことを禁止する。変更理由と新しい根拠をレビューする。
- コードの存在だけで実装完了とせず、テスト結果・実PDF照合・本番画面確認を別々に記録する。
- 未決事項をAIが暗黙に決定しない。候補、トレードオフ、必要な根拠を示して判断を求める。
- 既存仕様と矛盾する場合は、仕様を無視してコードを変更せず、先に影響範囲と移行案を提示する。

## 19. 現状の実装・検証状態を記録するルール

本書を使って開発を続けるAI／開発者は、作業開始時にリポジトリの実際のブランチ、コミット、コード、ワークフロー、テスト、データ構造を確認する。文書に記載された将来設計を、現行コードに既に存在すると仮定しない。

作業報告では必ず次を分ける。

- **実装済み**：コード／設定が存在する。該当ファイルとコミットを示す。
- **テスト済み**：具体的なテストを実行し、その結果を確認した。
- **実データ検証済み**：独立に確認した実PDFとの照合範囲と結果を示す。
- **公開確認済み**：実際の公開URLで確認した画面・成果物を示す。
- **承認済み**：品質・権利・公開の該当ゲートが記録されている。
- **未実施／未確認**：まだ確認していないものは明確にそう書く。

テストを実行できなかった場合、実行したように報告しない。合成fixtureの成功を実PDFの完全正確性へ拡張して報告しない。

### 22.1 共通原則

- 外部データごとに、公式ソースURL、データセット／系列ID、利用条件、取得頻度、タイムゾーン、観測対象日、公表時刻、取得時刻、改訂規則、欠損表現、単位を登録する。
- 取得物は可能な範囲で不変のraw archiveに保存し、SHA-256、取得URL、retrieved_at、known_at、ソース版／データセットID、取得実行IDを付与する。rawの保存・公開自体にも権利確認を適用する。
- raw、normalized、derived、deliveryを分離する。API応答やCSVを直接Web画面のソース・オブ・トゥルースにしない。
- 再取得・バックフィルは冪等にする。改訂値を黙って上書きせず、旧版・新版本体と差分を記録する。
- HTTP成功だけで取得成功と判定しない。コンテンツ形式、ヘッダー、列、型、件数、日付範囲、重複、欠損、鮮度を検証する。
- observation_date（観測対象日）、publication_at（公表時刻）、retrieved_at（取得時刻）、known_at（システムで利用可能になった時刻）、as_of（分析の情報締切）を区別する。バックテストは各時点で利用可能だったデータのみ使う。
- 取得遅延、欠損、API障害、レート制限、スキーマ変更、改訂を明示的に扱う。古い値を最新値のように見せない。
- APIキー等の秘密情報はGitへ保存せず、必要な場合はCI Secretで管理する。認証方式・プラン・利用条件は実装時に再確認する。
- データの取得権、内部保管権、派生分析利用権、再配布権、公開表示権は別々に確認する。公式サイトから取得可能であることは、自由な再配布を意味しない。

### 22.2 CFTC COT（参加者ポジショニング）

COTは、金市場の報告参加者区分ごとの週次ポジションを把握するために用いる。短期価格の直接予測ではなく、極端なポジショニング、変化、混雑の可能性を示す中期的なコンテキストとして扱う。

検討対象となった候補URL：
- Disaggregated CSV候補： https://publicreporting.cftc.gov/resource/72hh-3qpy.csv
- Futures-Only候補： https://publicreporting.cftc.gov/resource/gqe8-fqbz.csv
- Legacy Futures-Only候補： https://publicreporting.cftc.gov/resource/6dca-aqww.csv

重要：72hh-3qpyは、確認できたカタログ情報ではDisaggregated Futures-Onlyとされており、Futures-and-Options-Combinedとして扱ってはならない。他のIDも、対象レポート種別・金市場レコード・列定義を公式カタログと実データで確認するまでは採用確定しない。Combinedの別候補IDが見つかっても、公式メタデータと実データを照合するまで確定値にしない。

取込要件：
- 公式カタログ／APIメタデータ、レポート種別、列定義、データセットIDをSource Registryに記録する。
- 「Gold」という表示文字列だけで絞り込まず、市場コード、取引所、商品コード、レポート種別を検証する。
- ポジション基準日は通常火曜日、公開は通常金曜日だが、休日等による遅延を前提にし、固定日付だけで欠損判定しない。
- report_date（ポジション基準日）、publication_at、retrieved_at、known_at、レポート種別、long/short/spreading等の原列、派生net値を保持する。
- futures-onlyとfutures-and-options-combined、LegacyとDisaggregatedを混ぜて連続系列を作らない。
- 符号、単位、participant category、改訂、欠損・重複を検証する。欠損時に前週値で自動補完しない。
- 週次値を日次表示する場合、報告基準日と公表時刻を表示し、バックテストで公表前に利用可能だったと扱わない。
- net position、週次変化、OI比率、履歴パーセンタイル等はderived layerで計算し、元の報告値と分離する。

COTの受け入れ条件：
1. 公式カタログとデータセットID、レポート種別、列定義が一致する。
2. 実データでCOMEX Goldの対象レコードを独立確認できる。
3. 主要列、単位、符号、report date、欠損・改訂のテストが通る。
4. 同じ入力・同じルールで同じ正規化結果を再現できる。
5. point-in-timeテストで公表前の情報漏洩がない。

- FREDの公式CSV/API仕様を確認する。グラフ用CSV URLとAPIの利用条件・応答形式を同一視しない。
- APIを使う場合はキー要件を確認し、CI Secretで管理する。直接CSVの利用可否も実際のHTTP応答と利用条件で検証する。

- 金価格との関係は分析候補であり、因果関係や固定係数を前提にしない。

### 22.6 GLDオプション由来のGEX推定（GC先物取引の補助）

#### 目的とモデル境界

本プロジェクトで検討するGEXは、GLDオプションの公開データから推定したガンマ・エクスポージャーを、ゴールド先物（GC）の売買判断の補助情報として検証するモデルである。COMEX GCオプションから算出するGEXとは別の商品・別市場のモデルであり、GLDのGEXをGCのGEXと呼んだり、同じ単位の数値として直接比較・合算したりしない。

GLDオプションはGC先物オプションではない。GLDオプションのヘッジがGLD株式、金先物、その他の手段のどれで行われるかは公開OIだけでは分からず、GLDオプションのGEXからGCのヘッジ注文量を直接観測することはできない。GCへの影響は、GLDとGCのリターン関係を含む別途検証が必要な推定である。

#### データ取得候補と状態

候補プロバイダーはPolygon.io、EODHD、Alpha Vantage等。yfinanceはYahoo Financeの非公式ラッパーとして扱い、規約・可用性・履歴・安定性を確認せず本番の唯一のソースにしない。

- Alpha Vantageにはリアルタイム／履歴オプションの公式API仕様があるが、APIキー、プラン、歴史データの利用条件を確認する。
- EODHDは米国株・ETFオプションのEOD／履歴、OI、IV、Greeks等を提供すると案内しているが、GLDの実データのフィールド充足、履歴期間、価格、利用・再配布権は契約前に確認する。
- Polygon.ioのオプションAPIも候補だが、GLDの具体的なフィールド、OIの基準時刻、過去データ、プラン、ライセンスを確認する。
- この仕様追記時点でGLDの実レスポンス取得・完全性・計算値照合が済んだという意味ではない。最初の実装タスクは小規模な実データ取得試験とフィールド検証とする。

最低限必要なデータ候補：underlying symbol、option symbol、expiry、strike、call/put、OI、volume、IV、delta、gamma、option multiplier／contract specification、underlying price、quote/trade timestamp、OI as-of date、source/retrieval timestamp。提供されないフィールドは推測で補わず、未提供として記録する。

#### 計算層

1. まず満期別・ストライク別のCall OI、Put OI、総OI、Gamma、OI加重ガンマを、ディーラーのポジション符号を付けない形で表示する。
2. OI加重ガンマの基本形は Gamma × OI × contract_multiplier とする。ただしGammaの単位、オプション契約倍率、提供元の定義を確認し、ソースごとに検証する。
3. 1%の原資産価格変動に対する金額換算GEXの候補式は GEX_i = s_i × Gamma_i × OI_i × M_i × S² × 0.01。SはGLD価格、M_iは契約倍率、s_iは想定ポジション符号である。Gammaが原資産価格1ドル当たりのデルタ変化等の想定単位であること、倍率と単位換算が整合することを検証してから採用する。
4. OIは未決済契約数であり、ディーラーのネットポジションそのものではない。Call OIを常にプラス、Put OIを常にマイナスとする規則を実ポジションの事実として使わない。符号が観測できない場合、複数の符号シナリオを明示し、仮定依存性を表示する。
5. ガンマ・フリップ、gamma wall、strike concentrationは計算ルールを明示する。推定フリップは仮定に依存するモデル出力であり、観測された市場境界ではない。ガンマウォールを自動的に支持線・抵抗線や反発保証として扱わない。
6. 満期を無条件に全合算しない。満期別の値を保持し、対象満期窓、満期までの日数、当該満期を含める理由を明示する。
7. GLDのOI、Gamma／IV、原資産価格は可能な限り時間基準を整合させる。OIが前日基準なら当日リアルタイム値と混ぜて同時点データと表示しない。
8. GLDのGEXとCOMEX OG／GCのGEXを単純合算しない。比較する場合は別々の単位・原資産・契約仕様を保ち、検証済みの関係モデルを介する。

#### GLD GEXをGC取引に使うための検証

- GLDオプションの実データを取得し、必須フィールド、欠損、重複、OI基準日、契約倍率、Gamma単位を検証する。
- 独立実装または独立計算例と照合し、ストライク別計算を検証する。
- GLDとGCの価格・リターン・ボラティリティの関係を、取引時間、休日、価格乖離を考慮して推定する。単一の固定換算比率を仮定しない。
- 予測対象を明示する（例：将来一定期間の絶対リターン、実現ボラティリティ、レンジ突破、価格反転）。結果を見てから都合よく指標を選ばない。
- GEXなしのベースライン、符号仮定別モデル、満期窓別モデルと比較し、時系列順の訓練／検証／テスト分割、アウト・オブ・サンプル評価、手数料・スリッページを含む取引ルール評価を行う。
- 当時利用可能だったOI・IV・価格だけを使い、将来データ・改訂データの漏洩を防ぐ。
- ガンマ集中帯で値動きが抑制されるか加速するかは、符号・ディーラー在庫・流動性・イベント等に依存し、方向を固定しない。結果が再現しない場合、売買シグナルには採用しない。
- 画面では「GLDオプション由来・推定GEX」「データ基準時刻」「満期窓」「符号シナリオ」「仮定」「検証状態」を明示し、「ディーラーの実ポジション」や「GCの実測GEX」と表示しない。

#### GLD GEXの段階的な受け入れゲート

- GEX Gate A — Source feasibility：実際のGLDオプション応答を取得し、利用条件、履歴範囲、必要フィールド、タイムスタンプを確認する。
- GEX Gate B — Calculation correctness：Gamma単位、契約倍率、OI、価格の定義を確定し、独立計算と一致する。
- GEX Gate C — Point-in-time integrity：OI基準日、取得時刻、価格時刻、履歴改訂を保存し、時点リークがない。
- GEX Gate D — Predictive validity：GC先物のアウト・オブ・サンプル結果がベースラインに対して有用性を示す。改善がなければシグナル採用を見送る。
- GEX Gate E — Publication approval：データ契約、派生値の公開権、UI説明、更新監視を審査する。

### 22.7 外部データ・GEXの共通表示要件

- ソース、データ基準日、公表時刻（判明する場合）、取得時刻、最終更新、鮮度、欠損／改訂状態を表示する。
- 観測値、決定的な計算値、仮定付き推定値、売買シナリオを異なる表示区分にする。
- データが未取得・古い・検証不合格・権利未承認の場合は、最新・確定・公開可能であるかのように表示しない。
- 予測指標には定義、計算式、入力、仮定、対象期間、反証条件、検証結果を追跡できるようにする。
- 実データ取得試験、独立照合、権利承認、予測検証をそれぞれ別の完了条件として記録する。
